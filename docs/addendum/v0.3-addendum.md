# Programme Specification Addendum v0.3

Status: draft, to be developed further with the pilot team
Date: 27 September 2026
Relationship to baseline: extends the Master Specification v0.2, Technical
Architecture & Data Model v0.2 and YNLHN MVP Product Spec v1.0 (see
`docs/spec/`). Does not replace them. Where this addendum adds a new entity
or requirement type, the field/rule naming follows the conventions already
used in those documents.

This addendum captures five additions agreed during initial critique of the
v0.2/v1.0 specification set, plus a governance philosophy note:

1. Cross-organisation fatigue and safety
2. IMG / visa / Area-of-Need workforce module
3. Rural generalist procedural pathways
4. Telehealth / virtual care delivery mode
5. Multi-jurisdiction legal framework (scaling beyond SA)
6. Adaptive, risk-triggered governance (in place of upfront heavy governance)

---

## 1. Cross-organisation fatigue and safety

### Problem this closes

The v0.2 architecture already lists `FATIGUE` as a `Requirement` type
(Technical Architecture §12), evaluated against "work history + configured
limit." As specified, it only sees work booked *through this platform at this
organisation*. A doctor can be booked for a YNLHN shift via the platform and
a Wallaroo (or interstate) shift through a direct agency arrangement in the
same window, and neither side has visibility of the conflict. This is a live
clinical safety gap at single-LHN pilot scale, not only a statewide one.

### New entities

| Entity | Purpose | Key fields |
|---|---|---|
| `WorkEpisode` | Canonical record that a practitioner worked or is rostered to work at an organisation/site in a window | `id`, `practitioner_id`, `organisation_id`, `facility_id`, `start_at`, `end_at`, `source` (`PLATFORM_BOOKING` \| `SELF_DECLARED` \| `PARTNER_FEED`), `assurance_level`, `booking_id` (nullable) |
| `FatigueRule` | Versioned, configurable rule (min inter-shift break, max consecutive hours, max rolling 7/14-day hours) | `id`, `code`, `parameters_json`, `effective_from/to`, `status` (draft/published/retired) — same lifecycle as `RequirementSet` |
| `FatigueAssessment` | Computed result at interest-expression and again at booking confirmation | `id`, `practitioner_id`, `vacancy_id`, `assessed_at`, `status` (`PASS`/`FAIL`/`INDETERMINATE`), `rule_version`, `episodes_considered_json` |
| `FatigueDeclaration` | Doctor's own attestation of no conflicting external engagement in the relevant window | `id`, `practitioner_id`, `vacancy_id`, `declared_at`, `statement`, linked `WorkEpisode` rows it created |

### Rules

- A `WorkEpisode` sourced from `PLATFORM_BOOKING` is high assurance; one from
  `SELF_DECLARED` is explicitly lower assurance and must be visibly labelled
  as such wherever a `FatigueAssessment` is displayed.
- MVP scope: **hard gate** only on what the platform can know for certain
  (its own double-bookings for one practitioner). Anything relying on
  self-declaration produces `INDETERMINATE`, surfaced to Medical Workforce /
  approver as "cannot confirm no conflicting engagement — confirm with
  practitioner," never silently blocked and never silently passed.
- Becomes a genuine hard cross-organisation gate only once a shared
  `WorkEpisode` event feed exists across LHNs (Stage 3+ / statewide) — this
  is a direct, concrete first application of the "Workforce Trust Network"
  eventing architecture already described in the Master Specification's
  future-opportunity map, not a new architectural concept.
- New domain events: `WorkEpisodeDeclared`, `FatigueAssessed`,
  `FatigueOverridden` (override requires authority + reason + expiry + audit,
  consistent with every other override pattern in the v0.2 spec).

### Positioning

Frame this as a clinical-safety differentiator in the business case, not
only a compliance feature — no other AU locum platform currently appears to
give a health service or a doctor shared visibility of cross-organisation
fatigue exposure.

## 2. IMG / visa / Area-of-Need workforce module

### Problem this closes

The v0.2 credential model has one generic "Identity/work rights" category.
Rural and remote SA locum workforce is disproportionately International
Medical Graduates (IMGs), often on provisional/limited Ahpra registration,
subject to visa conditions, 10-year moratorium / District of Workforce
Shortage (DWS) restrictions, and facility-specific Area-of-Need (AoN)
determinations. None of this is structured in the current model, yet it is
plausibly the single biggest practical blocker to mobilisation for this
cohort — more so than clinical ScopeGrant status.

### New entities and fields

| Entity/field | Purpose |
|---|---|
| `CredentialDefinition` category `IMMIGRATION_WORK_RIGHTS` | Visa subclass (482/494/186/491/other), visa conditions, VEVO check result, next-check-due date |
| `PractitionerCredential.registration_type` | Explicit Ahpra registration type: general / provisional / limited / supervised-practice — feeds `ScopeGrant.supervision_level`, which already exists in v0.2 and just needs this populated meaningfully for this cohort |
| `AreaOfNeedDetermination` | New organisation-issued authorisation entity, modelled like `ScopeGrant`: `practitioner_id`, `determining_authority`, `facility_id`/`position_id`, `classification`, `effective_from/to`, `status`. **Not** practitioner-portable — facility/position-specific, independently issued, never inferred from a prior determination elsewhere |
| `MoratoriumStatus` | Commonwealth 10-year moratorium / DWS restriction — a location-restriction gate independent of clinical eligibility. A vacancy outside a DWS area can be ineligible for a moratorium-restricted practitioner regardless of ScopeGrant status |
| `EnglishLanguageTestResult` | IELTS/OET result as a credential type with its own validity window |

### New `Requirement` types

- `AREA_OF_NEED` (hard) — evaluates current `AreaOfNeedDetermination` against
  the vacancy's specific facility/position.
- `MORATORIUM_LOCATION` (hard) — evaluates DWS/moratorium status against the
  vacancy's location, independent of `ACTIVE_SCOPE`.
- `VISA_WORK_RIGHTS` (hard) — evaluates current visa condition/VEVO status.

### Sensitivity and integration notes

- Immigration/visa data sits in the **highest** sensitivity compartment —
  stricter than general identity evidence. It must be excluded from *every*
  default `CredentialShare` bundle, not merely unselected by default, given
  the discrimination/vilification risk of inadvertent disclosure.
- VEVO (Department of Home Affairs, Visa Entitlement Verification Online) is
  free and already exists — a materially simpler and lower-governance-risk
  automated integration than the Ahpra primary-source verification the v0.2
  roadmap defers to "P1/P2." Worth sequencing earlier.

## 3. Rural generalist procedural pathways

### Problem this closes

v0.2's `RoleTemplate` worked examples are ED Senior/ED RMO only ("FACEM or
configured equivalent"). SA's most acute, visible rural workforce failure
mode is procedural rural generalist coverage — obstetric and anaesthetic
service suspensions — not ED staffing gaps. The current examples under-serve
the harder, higher-value case.

### New entities

| Entity | Purpose |
|---|---|
| `ProceduralEndorsement` | Distinct from `PractitionerCredential` because currency is usually **case-count/CPD-based**, not date-expiry-based. Fields: `practitioner_id`, `endorsement_type` (anaesthetics / obstetrics ± surgical / surgery / emergency medicine / mental health / adult internal medicine / paediatrics / Indigenous health), `awarding_body`, `awarded_at`, `currency_status`, `case_count_window_json` |
| `Placement` | Aggregate above `Booking` for non-contiguous block/on-call engagements under one arrangement (e.g. "1 week per month for 6 months") — the standard procedural rural generalist coverage pattern, which single-shift `Booking` does not represent. Fields: `practitioner_id`, `organisation_id`, `role_template_id`, `start_date/end_date`, linked `Booking` rows |

### `Requirement` model extension

`Requirement.parameters_json` needs to support rolling case-count thresholds
(e.g. "minimum 20 supervised deliveries in the last 24 months"), not only
simple date-expiry checks — extends the generic `EXPERIENCE` requirement
type already defined in v0.2 rather than replacing it.

### New `RoleTemplate` seeds

`RURAL_GENERALIST_BASE`, `RURAL_GENERALIST_OBSTETRICS`,
`RURAL_GENERALIST_ANAESTHETICS`, `RURAL_GENERALIST_SURGICAL` — each layering
base Fellowship (FACRRM / RACGP-RG) + procedural endorsement + facility-
specific procedural privileging (arguably the highest-stakes `ScopeGrant` in
the system, since it gates theatre/birthing-unit access).

### Strategic note

Positioning part of the narrative around "procedural rural generalist
service-continuity risk" rather than only "ED locum staffing" is likely a
stronger case for SA Health/DPC funding conversations, since service
suspensions in this category are the visible symptom driving current policy
attention.

## 4. Telehealth / virtual care delivery mode

### Why this belongs earlier than "future scope"

The eligibility/scope engine already generalises to a virtual delivery mode
with no new architecture required — it is a materially cheap extension, not
a distant horizon item, because it removes travel/accommodation/on-call-
location complexity rather than adding to it.

### Model additions

| Addition | Detail |
|---|---|
| `delivery_mode` enum on `RoleTemplate` and `Vacancy` | `IN_PERSON` \| `TELEHEALTH_SYNCHRONOUS` \| `HYBRID` |
| `Requirement` type `TELEHEALTH_MEDICARE_ELIGIBILITY` | Evaluates existing/relevant-relationship rules under Medicare telehealth item numbers |
| `Requirement` type `CROSS_BORDER_PRESCRIBING_AUTHORITY` | A doctor physically located in one state supporting a patient/service in SA raises jurisdictional prescribing questions distinct from Ahpra registration itself — flagged for legal review (§5) before enabling interstate telehealth |
| `Requirement` type `TECHNOLOGY_CREDENTIAL` | Local telehealth platform/system access training — small but real onboarding item |

### Sequencing recommendation

Introduce telehealth-eligible `RoleTemplate`s in Stage 1/2 rather than
treating virtual care as purely future scope. It is a direct, sooner
realisation of the "emergency workforce mobilisation" opportunity the
Master Specification already names as a later horizon, and demonstrates the
eligibility engine's genericity early and cheaply.

## 5. Multi-jurisdiction legal framework

This section is a **map of what varies by state and needs formal legal
review as the programme scales past SA** — it is not legal advice and does
not draw legal conclusions. Engage a health/privacy lawyer, ideally one with
SA Health and Commonwealth grant-funding experience, given the tri-party IP
structure (see below).

| Dimension | Nationally uniform? | What varies | Review trigger |
|---|---|---|---|
| Practitioner registration | Yes — Ahpra / National Law | — | — |
| Health information privacy | **No** | SA has no dedicated privacy act (Cabinet Information Privacy Principles + Health Care Act 2008 s93 confidentiality); NSW: Health Records and Information Privacy Act 2002; Vic: Health Records Act 2001 + Privacy and Data Protection Act 2014; Qld: Information Privacy Act 2009; Tas: Personal Information Protection Act 2004; ACT: Health Records (Privacy and Access) Act 1997 + Information Privacy Act 2014; NT: Information Act 2002 | Before any second-state pilot or any cross-border data flow |
| Organisational credentialing / scope-of-practice process | No (ACSQHC guidance is advisory/accreditation-linked, not legislated uniformly) | Each state health department sets its own clinical governance framework | Confirms the "scope stays local, never inferred" design is a legal necessity, not only good practice |
| Area of Need / moratorium | Partially — moratorium/DWS is Commonwealth (Health Insurance Act); AoN classification is state-administered | Determining authority and process differ per state | Before enabling `AreaOfNeedDetermination` outside SA |
| Industrial / employment | No | Awards, enterprise agreements, payroll-tax nexus, cross-border workers' compensation rules all differ by state | Before any interstate booking/timesheet flow |
| Medical indemnity | Commonwealth-regulated at a high level (Medical Indemnity Act, run-off cover scheme) | Product coverage terms and state-of-practice scope vary by insurer/state | Before using indemnity currency as a hard gate across states |
| Locum procurement policy | No | Each state runs its own panel/procurement framework (SA Health's Use of Locums Policy and Panel Contract are SA-specific) | Before configuring `SourcingPolicy` for a new jurisdiction |
| IP / data ownership | N/A | Tri-party arrangement (1/3 founder, 1/3 SA Health, 1/3 Department of the Premier and Cabinet) is novel and undocumented in the v0.2 spec set | Before seeking grant funding or engaging a second LHN/state. The credential ontology and canonical data model are explicitly named "the durable asset" in the SA Statewide Business Case §27 — ownership of *that specifically* should be settled separately from, and before, ownership of the codebase |

### Recommended approach (matches the adaptive governance philosophy below)

Treat this table as a set of trip-wires rather than a standing legal
committee: each row gets formal review only when its trigger condition is
about to occur (second LHN, second state, first grant agreement, first
Commonwealth co-investment conversation) — not upfront, and not all at once.

## 6. Adaptive, risk-triggered governance

The v0.2 Implementation & Evaluation Plan specifies ten workstreams, a
steering group with nine-plus named specialist roles, and five reporting
cadences (§7–8, §26 of that document). That is appropriate for a funded,
multi-LHN production rollout. It is disproportionate for a small, co-design-
led pilot at two sites, and risks the coordination overhead outweighing
delivery capacity before any code ships.

**Decision for this build**: keep only what is safety- or legal-exposure-
critical fixed from day one; let everything else emerge with the project as
real risks surface.

### Fixed from day one (non-negotiable, enforced in code, not policy)

- Scope authority is never inferred from portable evidence — `ScopeGrant` is
  always organisation-issued and never practitioner-editable.
- Eligibility is never optimistic on missing data — `INDETERMINATE`, never a
  default `ELIGIBLE`.
- Locum Experience feedback anonymity threshold is enforced by the query
  layer itself (minimum-n suppression), not by dashboard convention.
- Basic MFA and access separation for credential evidence, commercial data
  and confidential feedback.

### Emergent (build governance alongside the pilot, not ahead of it)

A short trip-wire list in place of a standing committee structure, e.g.:

- Credential fraud detected → escalate to [named process, TBD with pilot team]
- Privacy complaint raised → escalate to [named process, TBD]
- Scope/eligibility error observed → escalate to Clinical Safety lead, TBD
- Second LHN or second state engagement proposed → trigger the relevant row
  of the §5 legal table

This list should grow only in response to an actual observed risk during
co-design and pilot testing, consistent with "governance will be developed
as risks are exposed."
